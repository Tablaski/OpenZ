# Contributor and agent instructions

- Use `dev` for development and `main` for stable versions. Do not create extra branches unless requested.
- The only Unity project is `source/`. Edit its files directly; do not create a second source tree or copy/patch installation step.
- Write all new code, comments, documentation, commit messages and player-facing text in English.
- Preserve upstream OpenZ names, credits, licenses and existing content. Do not translate or rename upstream content as part of unrelated changes.
- Preserve the upstream code-only Git layout: track `source/Assets/OpenZ/Scripts/`, `source/Assets/OpenZ/Shaders/`, their metadata, `source/Packages/` and `source/ProjectSettings/`. Multimedia and scenes remain local and are not covered by a Git commit.
- Do not add Git LFS or import multimedia into Git. Do not commit Unity caches, personal settings, generated project files, logs or compiled players. If work changes an ignored resource, arrange its separate backup/distribution explicitly before delivery.
- Only compile or package a Unity player when the user explicitly requests a game build. Do not launch a player build automatically for development or validation. Source checks and logic or simulation tests remain allowed; compiling a test harness does not count as building the game.
- Before delivery, run the checks appropriate to the change that do not require an unrequested player build. Clearly distinguish completed checks from validation that still needs a freshly built player, including menu, rendering, runtime and native integration checks.
- Notify the user when a substantial set of features has accumulated since the last build they tested, or after a broad code change with a meaningful regression risk that warrants a build. Explain why a build would be useful and wait for the user to request it; a recommendation is not authorization to build.
- When the user requests a build, produce the final release version of the game, not a development or debug player. Disable development builds, script debugging, profiler connections and other development-only options.
- After compilation, do not launch, play, automate, inspect screenshots of, or run native integration checks against the game unless the user explicitly asks for those tests. The user performs game testing. Do not spend tokens or time attempting post-build gameplay or UI validation. Only check the build process result and report completion and the output location.
- Keep a persistent record of changes awaiting player validation. A successful build does not mark those checks as passed: leave them pending for the user's manual testing unless the user explicitly requests agent testing. If testing is explicitly requested, group the requested checks on the same release player and report what passed, failed or remains pending.
- Commit completed work with the repository's configured GitHub identity, push it to `origin/dev`, and verify the remote commit. Do not change the user's identity to a placeholder.
- Preserve the user's personal email privacy: use the configured GitHub noreply address.
- A playable release must contain the entire player output folder and identify its source commit. Do not describe a source commit as a downloadable player release.
- A user request to "release" authorizes pushing the completed source to GitHub, updating the public README and version changelog, rebuilding the release ZIPs and uploading them to GitHub. Increment the fork/release version for future releases. The current 0.2.7 replacement is an explicit one-time exception: replace its previous build and assets while retaining version 0.2.7.
- Multiplayer tank and robot dynamics are host-owned lobby rules, frozen for the match. Do not offer profile changes in the in-game options. Clients may inspect lobby rules but cannot edit them.
- Keep every OpenZ/OpenZ-VK logo dark orange. Use violet to identify fork-added game options outside the lobby; the lobby itself uses the ordinary orange/neutral presentation.

## OpenZ-VK presentation and compatibility

- Brand the fork as OpenZ-VK in the main menu, Unit Editor, in-game HUD, multiplayer screens and other player-visible identity marks. Keep the fork identity visible in screenshots and recordings, including end screens. Preserve upstream credits, licenses, reference-stat names and internal OpenZ namespaces/assets.
- Keep the fork version independent of upstream OpenZ. The single source is OzForkVersion.Number. Increment it for each delivered feature/fix set; never reuse a version for a changed release. Every requested player build must include FORK_BUILD.json with the source commit, modified-tree flag and UTC build timestamp, and show that identity at the bottom right. An unstamped player must clearly say UNSTAMPED BUILD. A source update is not a player release.
- In every options menu outside the lobby, keep upstream options first and group fork-added options after them on each relevant tab. Use the exclusive OpenZ-VK violet accent (#D570FF) and the shared OzForkOptions classification/highlight/order helpers. Register every future fork option there; keep complete fork-only settings sections visibly branded too. The entirely new lobby uses orange/neutral controls without violet fork highlighting.
- Preserve the user's game configuration across updates and builds. Keep the existing PlayerPrefs company/product identity (OpenZ/OpenZ), established keys, value meanings and persistent data directory even when display branding changes. Never reset preferences or replace existing choices with new defaults. Add explicit, non-destructive migrations when a schema/key/value must change; maintain backward compatibility where possible.
- Version and maintain the local preference history (OzForkPreferences.Schema and its key manifest). Include newly added preferences, preserve unknown keys, and snapshot changed non-sensitive game/presentation settings locally under Application.persistentDataPath/OpenZ-VK/preferences/. Keep personal configuration, devices, credentials and backup history out of Git and release archives. Track schema, migration logic and defaults in Git; maintain the user's actual choices locally. Document any configuration that cannot be carried forward.
- Distinguish ORIGINAL OpenZ production rules from optional VK balancing rules in labels and help. A disabled territory cap restores the original territorial advantage; it does not disable territorial bonuses. The fort loser bonus is an independent, optional setting based on offensive mobile-unit production value, not territory counts.
