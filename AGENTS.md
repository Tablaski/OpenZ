# Contributor and agent instructions

## Public presentation and build delivery

- Call the runnable game a "compiled game", never a "player", in documentation and user-facing explanations. Reserve "player" for a person playing the game; internal Unity API identifiers may retain their technical names. Briefly distinguish source code, compiled-game ZIPs, Unity, resource ZIPs and the installer in the README.

- Always put the supplied OpenZ-VK logo at the very beginning of the public README, before notices and headings. Do not use the original OpenZ banner as the opening image. Preserve the supplied logo's artwork and colors.
- Keep the README short and focused on differences from original OpenZ, especially added gameplay options, multiplayer rules and converted AI Maps. Technical implementation and optimization details belong in commits, commit descriptions or technical documentation.
- The public changelog and installer release notes are always for players, never a developer changelog. Describe new features, gameplay and rule changes, installation/update improvements and visible fixes in plain language. Keep implementation details, internal identifiers, tests, benchmarks, source-only delivery notes and publication/review procedures in commits and their descriptions or private validation records. Apply this rule to future entries and revisions of existing fork entries.
- For every delivered OpenZ-VK version, add a player-facing `## OpenZ-VK <version> (<date>)` entry to `docs/CHANGELOG.md` before packaging, with the newest version first. Changes & Updates uses this file for its OpenZ-VK tab and Unity embeds it in compiled games. Keep the fork introduction aligned with the README, credit ValKognito and link to OpenZ / ZZone Discord. Keep the original OpenZ history in its own tab and verify both tabs when preparing a release.
- Public README, release notes and player-facing presentation must not state or imply AI/Codex authorship of the project. Explicit user-approved exception: describe AI Maps as low-cost AI reproductions of original Z maps. Keep the README focused on the fork goals, magic-link 1 vs 1, optional balance and community-assisted work toward 1996 combat tactics; omit detailed boost settings. Put the OpenZ/ZZone Discord link immediately after the opening logo.
- Screenshots may illustrate substantially changed screens and key features; several AI Maps screenshots are useful. Do not add a screenshot just to showcase the original logo.
- Every future Windows build must include a clearly named `Unit Editor/` directory with a direct editor launcher. Share the main player's runtime files rather than duplicating the entire game.
- Official Windows releases must include the standalone installer with the supplied OpenZ-VK logo, update manifest and range-download payload packs, alongside complete fallback player ZIPs. The installer requires no Git and preserves the OpenZ preferences directory.
- Keep two installer paths: published players without Unity, and source retrieval/builds from any selected `main` or `dev` commit with Unity. Detect and use installed Git; offer its optional installation initially, and use commit snapshots when Git is absent. Detect/guide the required Unity editor and retain source resources across revisions. Maintain changelogs, update notices and the one-time source resource bundle alongside player downloads.
- After a replacement release has been verified, remove obsolete local player builds and release ZIPs at the user's request. Keep the current release, source assets, map packages and backups of untracked resources.
- Name the converted-map catalog AI Maps in solo and multiplayer. Use the AI stamp and robot head on AI map previews. Offer Allowed units on solo mission selection as well as in the lobby; keep solo choices separate from host-owned multiplayer rules.

- Use `dev` for development and `main` for stable versions. Do not create extra branches unless requested.
- Publish compiled-game ZIPs, installer payloads and GitHub Releases only for the latest stable version on `main`. A request to release, publish or make a GitHub release on `dev` means pushing the completed source commit to `origin/dev` and verifying it there. Do not create a GitHub Release, tag, ZIP or installer payload for `dev`. A separately requested local build remains local. The existing installer's source workflow retrieves the chosen `dev` revision and compiles it with Unity, reusing the independently versioned OpenZ 1.4 base resource package pinned in `SOURCE_RESOURCES.json`. Publish a new resource bundle only when the base resource package changes.
- The only Unity project is `source/`. Edit its files directly; do not create a second source tree or copy/patch installation step.
- Write all new code, comments, documentation, commit messages and player-facing text in English.
- Preserve upstream OpenZ names, credits, licenses and existing content. Do not translate or rename upstream content as part of unrelated changes.
- Preserve existing OpenZ features and gameplay rules. Before removing an upstream feature or rule that the user has not explicitly asked to remove, ask for confirmation. When proposing an alternative behavior, provide a setting that lets the user choose between the original and the alternative.
- Preserve the upstream code-only Git layout: track `source/Assets/OpenZ/Scripts/`, `source/Assets/OpenZ/Shaders/`, their metadata, `source/Packages/` and `source/ProjectSettings/`. Multimedia and scenes remain local and are not covered by a Git commit.
- Explicit user-authorized exception: track the lightweight `aimaps/` local Unity package, including native map data, decoded grids, generated minimaps, converted scenes and small shared materials/textures. Its scenes reference the existing local OpenZ assets; do not duplicate the large base models, textures, audio or resource archives there. A normal Git pull must carry map updates without an extra resource ZIP or manual copy step.
- Do not add Git LFS or import multimedia into Git. Do not commit Unity caches, personal settings, generated project files, logs or compiled players. If work changes an ignored resource, arrange its separate backup/distribution explicitly before delivery.
- The user grants standing permission to compile the game locally for development, validation and requested captures. Keep development builds local. Package or publish release assets only under the stable-release rules above.
- Before delivery, run the checks appropriate to the change that do not require an unrequested player build. Clearly distinguish completed checks from validation that still needs a freshly built player, including menu, rendering, runtime and native integration checks.
- Notify the user when a substantial set of features has accumulated since the last build they tested, or after a broad code change with a meaningful regression risk that warrants a build. State what the local build covers and what still needs manual validation.
- When the user requests a build, produce the final release version of the game, not a development or debug player. Disable development builds, script debugging, profiler connections and other development-only options.
- After compilation, do not launch, play, automate, inspect screenshots of, or run native integration checks against the game unless the user explicitly asks for those tests. The user performs game testing. Do not spend tokens or time attempting post-build gameplay or UI validation. Only check the build process result and report completion and the output location.
- Keep a persistent record of changes awaiting player validation. A successful build does not mark those checks as passed: leave them pending for the user's manual testing unless the user explicitly requests agent testing. If testing is explicitly requested, group the requested checks on the same release player and report what passed, failed or remains pending.
- Commit completed work with the repository's configured GitHub identity, push it to `origin/dev`, and verify the remote commit. Do not change the user's identity to a placeholder.
- Preserve the user's personal email privacy: use the configured GitHub noreply address.
- A playable release must contain the entire player output folder and identify its source commit. Do not describe a source commit as a downloadable player release.
- A stable release on `main` authorizes pushing completed source to GitHub, updating the public README and version changelog, rebuilding the complete Windows ZIPs and installer assets, and uploading them to GitHub. Increment the fork version for each delivered change. Retaining version 0.2.7 for its replacement release was a one-time exception.
- Multiplayer tank and robot dynamics are host-owned lobby rules, frozen for the match. Do not offer profile changes in the in-game options. Clients may prepare a local grouped proposal; only host acceptance changes official rules. Expire proposals and require draft refresh after an official revision change.
- Keep text-only OpenZ/OpenZ-VK wordmarks dark orange; preserve the supplied image logo and its original colors. Use violet to identify fork-added game options outside the lobby; the lobby itself uses the ordinary orange/neutral presentation.

## OpenZ-VK presentation and compatibility

- Pin the required base asset package independently of the fork version in SOURCE_RESOURCES.json. Resource updates must verify hashes, reuse unchanged data, preserve unknown files and back up modified managed assets before replacement. Never treat a legacy resources-ready marker alone as proof of compatibility. Validate the resource package and embedded build identity when the player starts; block incompatible installations with repair guidance. Keep source compilation and published-player installation as separate guided wizard flows, with a readable changelog and tool setup buttons disabled when already available.

- Brand the fork as OpenZ-VK in the main menu, Unit Editor, in-game HUD, multiplayer screens and other player-visible identity marks. Keep the fork identity visible in screenshots and recordings, including end screens. Preserve upstream credits, licenses, reference-stat names and internal OpenZ namespaces/assets.
- Keep the fork version independent of upstream OpenZ. The single source is OzForkVersion.Number. Increment it for each delivered feature/fix set; never reuse a version for a changed release. Every requested player build must include FORK_BUILD.json with the source commit, modified-tree flag and UTC build timestamp, and show that identity at the bottom right. An unstamped player must clearly say UNSTAMPED BUILD. A source update is not a player release.
- In every options menu outside the lobby, keep upstream options first and group fork-added options after them on each relevant tab. Use the exclusive OpenZ-VK violet accent (#D570FF) and the shared OzForkOptions classification/highlight/order helpers. Register every future fork option there; keep complete fork-only settings sections visibly branded too. The entirely new lobby uses orange/neutral controls without violet fork highlighting.
- Preserve the user's game configuration across updates and builds. Keep the existing PlayerPrefs company/product identity (OpenZ/OpenZ), established keys, value meanings and persistent data directory even when display branding changes. Never reset preferences or replace existing choices with new defaults. Add explicit, non-destructive migrations when a schema/key/value must change; maintain backward compatibility where possible.
- Version and maintain the local preference history (OzForkPreferences.Schema and its key manifest). Include newly added preferences, preserve unknown keys, and snapshot changed non-sensitive game/presentation settings locally under Application.persistentDataPath/OpenZ-VK/preferences/. Keep personal configuration, devices, credentials and backup history out of Git and release archives. Track schema, migration logic and defaults in Git; maintain the user's actual choices locally. Document any configuration that cannot be carried forward.
- Distinguish ORIGINAL OpenZ production rules from optional VK balancing rules in labels and help. A disabled territory cap restores the original territorial advantage; it does not disable territorial bonuses. The fort loser bonus is an independent, optional setting based on offensive mobile-unit production value, not territory counts.
